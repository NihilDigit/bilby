# 订阅动态流单源化

2026-08-24。首页与「其他动态」合并为同一条流,专栏投稿进首页。本文是这次改动的权威记录:
拍板过的决定、被替换掉的旧设计,以及它为什么错。

## 症状与根因

四个症状:取关的 UP 不会从首页消失;排除某个 UP 的状态在各处表现不一;「上次看到这」那条
横条活满整个进程;首页与「其他动态」分两次请求。

根因是同一个:**本地状态全是追加式的,没有任何一条路径能表达「这一条不在了」**。

| 状态 | 从前的写入 | 能删吗 |
|---|---|---|
| Room 缓存 | `mergeHead` / `appendTail`,全是 upsert | 只有按条数砍最旧 |
| VM 的 `allItems` | `mergeFeedAtHead` | 不能 |
| 排除名单 | DataStore + VM 里一个 `var` 副本 | 只能整份清空 |
| 已读位置 | DB 连续写 + VM 里一份冻结快照 | 快照永不作废 |

`mergeFeedAtHead` 返回 `newAtHead + refreshedRest`,`refreshedRest` 把旧列表原样留着。这个
函数的语义里没有「消失」这种可能,所以取关之后那个人的投稿只会等着被 500 条上限挤出去。

把「缓存」当成了「列表的持久化」,而不是「一次响应的副本」。前者要求本地能独立演化,那就
必须自己实现删除;后者只要能重建,删除是免费的。

## 现在的形状

**一条流,一个游标,在 `data/DynamicFeedStore.kt`。** 不变式只有一条:列表就是从服务端连续
取到的那几页,游标指向再下一页。刷新即整段重取,翻页即续接。

- `DynamicRepository.loadFeed` 只发 `type=all`,一页里的每一条在解析时分流(`toFeedPage`)。
- 自动翻页的判据是「要用它的那一半拿到了几条」,另一半的收获照样入库 —— 同一次请求同时喂
  两个视图,这是合流之后最实际的好处。上限 3 页,防坏数据死循环,不是内容策略。
- 排除名单在读出去那一步过滤(`combine`),不写进列表:排除可撤销,烤进列表就回不来了。
  过滤在 store 里做,两个视图因此天然一致。
- 缓存只存首页那一半的最新一段,整段替换(`FeedCacheRepository.saveHead`)。翻页翻出来的
  更旧内容不落盘,进程结束就没了。DB 升到 v7,续接游标表删除。

## 拍板记录(owner 定)

- **排除的语义是「不看他的投稿」**,理由是有些 UP 刷屏。作用于时间序流的两半(首页与
  「其他动态」),不作用于「正在直播」「最常访问」那两排 —— 那是导航,不是时间线。
- **已读线每次进屏重取一次快照**(候选 A)。进屏期间不跟着落盘更新,否则线会追着滚动位置跑。
  另一个候选是「越过之后本次不再画」,被否:往回翻的人会找不到分界。
- **深翻的内容不保留**。翻页只在内存里。这一条决定了游标不必落盘,连带删掉了
  `hasEstablishedCursor`、`appendTail`、`advanceCursor` 那一整套「头部刷新不许覆盖已翻到的
  深度」的判断。
- **专栏提到首页之后,「其他动态」里不再保留一份**。否则那一页不再是「首页没有的那一半」。

## 「真正的文章」怎么认

判据是 `major.opus.summary.has_more` —— 服务端说正文在这里被截断了,也就是界面上「阅读
全文」那个入口在不在。图文和短动态没有它。

不看动态类型:带着 `itemOpusStyle` 请求时,一篇几千字的长文的 `type` 常常是
`DYNAMIC_TYPE_DRAW`。也不看有没有标题:同一个 features 位会把纯文字动态的第一行提成
`opus.title`,「有标题就是专栏」这条曾经写在 `notes/dynamic-cards.md` 里,真机上不成立,
已一并更正。实测数据在 `api/dto/DynamicDto.kt` 的 `OpusSummaryDto.hasMore`。

认不出编号(`/opus/<id>` 或 `/read/cv<id>`)的不算文章:它没有自己那一页,点开无处可去。

首页里一条专栏和一条视频共用 `VideoRow` 的版式,封面角标那一格写「文章」而不是时长,
正文摘要占 `note` 那一行。不另画一种行 —— 版式差一点点在滑动时看得出接缝。

## 条目模型

首页条目从 `FeedItem` 变成密封的 `FeedEntry`(`Video` / `Article`)。列表键、已读位置、
排除名单都只认 `FeedEntry.id`:视频是 bvid,专栏是 `opus<id>` 或 `cv<id>`。
`feed_read_position.lastReadBvid` 随之改名 `lastReadEntryId`。

## 已知取舍

- 刷新会把列表整段换成新取到的头部,深翻的部分随之丢掉。刷新只在列表顶部触发,而「以服务端
  为准」和「保住已翻到的深度」不可兼得 —— 后者正是旧设计里那份没人能删掉东西的第二真值。
- 「其他动态」在任一侧刷新时也会重置。它们本来就是一条流。
- 一次只发一条请求,抢不到锁的那次直接返回不排队:排队的那次醒来时看到的是已经变过的游标。
